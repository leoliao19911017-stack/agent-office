三、数据模型与迁移 v9

  └── workflow_run_steps（九步之一，如 05）
        └── tasks.workflow_run_id + tasks.workflow_step_id   ← 这一列关系就是本次加的

四、API 行为

方法与路径行为
POST /api/tasks可带 workflow_run_id / workflow_step_id；带了就校验：run 不存在 → 404 RUN_NOT_FOUND，run 里没这步 → 404 STEP_NOT_FOUND，只给步骤不给 run → 400 BAD_WORKFLOW_LINK；三种情况都不建任务
GET /api/tasks?workflow_run_id=X只返回这次需求的任务（SQL 过滤，走联合索引）；响应回显 workflow_run_id / workflow_step_id
GET /api/tasks?workflow_run_id=X&amp;workflow_step_id=05只要这一步的；可与 include_archived=1 叠加
GET /api/tasks（不带参数）原行为不变：全量列表，没挂工作流的老任务照常返回
GET /api/tasks 每一项多三个字段：workflow_run_id、workflow_step_id、workflow_step_name（服务端按 run 的模板版本查出，查不到为 null）
POST /api/workflow/runs/:runId/steps/:stepId/tasks新增。 body { tasks: [{ title, acceptance? }, ...] } → 201 { ok, created, tasks: [...], workflow_run_id, workflow_step_id, workflow_step_name, actor }

批量建任务的语义：

  • 整批全建或全不建。 先把每一项校验完（任一项没有 title → 400 BAD_TITLE，指明 tasks[i]），再在一个事务里写入，中途出错整批回滚。理由：任务书是一个整体，半批任务 + 调用方重试 = 重复任务。这和上一轮的 /api/tasks/batch（归档 / 删除，逐条独立、允许部分失败）刻意不同。
  • tasks 不是非空数组 → 400 BAD_TASKS；路径对但方法不是 POST → 405。
  • 路径上的 run / 步骤先校验（不看 body）：run 不存在 → 404 RUN_NOT_FOUND；run 里没有这一步 → 404 STEP_NOT_FOUND。错误码沿用 /api/workflow/runs* 引擎里已有的那两个。
  • 建任务不推进步骤、不碰状态机。
  • 同一批的时间戳逐条 +1ms：列表按 updated_at 倒序，这样整批顺序确定（后建的在上），不会因为时间戳全相同而退化成按随机 task_id 排。

归档 / 删除 / 恢复 / 批量的代码路径一行没改，并且用挂了工作流的任务重新验过（B10 用例 + 截图脚本里真点了一次归档再恢复）。

五、界面（web/board-cromma.*）

  • 任务区多一行「工作流」下拉。 选项来自 GET /api/workflow/runs；选中哪次需求，任务列表就真请求 /api/tasks?workflow_run_id=…（服务端过滤，不是前端筛），和「显示已归档」是同一个做法。选「全部任务」回到不过滤。

多出来的那条是什么（第 1 次）： test/g07-pages.test.js 的 A1「首页驾驶舱首屏」挂在 consoleErrs 断言——首页加载时有一个请求拿到 500。查证过程：

  • 这个文件不引用我改的任何东西（api/tasks、board-cromma、workflow、lib/tasks 均无）。
  • 单独复跑该文件 2 次，都是 4/4。
  • 写了个「金丝雀」：全量套件并行跑的同时，用同一个 G07 夹具反复加载首页（共用同一个临时库）。57 次加载，0 个 5xx，0 条服务端错误。（脚本：docs/runs/run-3d22e663/probes/canary.mjs）
  • 怀疑是「多个进程同时第一次打开同一个还不存在的库」。单独做实验：10 个真实 web/server.js 同时第一次打开同一个新库、同时各发 2 个首个请求。3 轮分别有 18/20、18/20、5/20 个请求 500，服务端 stderr 是（脚本：probes/first-open-race.mjs）：

（存档：first-open-race.log。）

结论与边界：

  • 这是 openDb / applyMigrations 的既有并发缺陷：没有任何跨进程串行化，多个进程同时首次创建并迁移同一个库时会锁冲突。不是 v9 引入的，也不是这次任务范围内的东西，我没有改它。
  • 我没有定位到真实流程里具体是哪条语句锁住。我另做了一个简化复刻，撞出来的是 duplicate column name（那个复刻没有「先查列再 ALTER」），和真实服务里的 database is locked 不是同一条语句——所以这里只能说清现象和出错层级，说不清具体语句。
  • 对线上的影响：只发生在「多个进程同时首次创建一个新库」时。生产库已存在（WAL 模式），8090 是单进程，重启不会触发。
  • 建议的修法（另开一个小改动做，配并发打开的测试）：applyMigrations 每个版本用 BEGIN IMMEDIATE 包住，进事务后重读 schema_version，别人迁过就跳过；busy_timeout 提到 journal_mode 之前设。

十、技术选择（自己判断的，说明理由）

选择理由你可能想改的地方
只给 workflow_step_id 不给 workflow_run_id → 400（写入和查询都这样）「05」这种步骤号只在一次 run 里有意义，半截挂点没法追溯是哪次需求如果想要「跨所有 run 看第 05 步的任务」，放开查询侧是一行的事
POST /api/tasks 带了 run 就校验存在性（404）不让任务挂到不存在的 run / 步骤上，和批量接口口径一致任务书只写了「接受」这两个字段，没写校验
批量建任务整批原子任务书是一个整体；部分成功 + 重试 = 重复任务如果更想要「逐条结果、允许部分失败」，要另定口径
同批时间戳逐条 +1ms列表按 updated_at 倒序，整批顺序才确定副作用：后建的几条 created_at 比请求时刻晚几毫秒
两列不加外键run 归档 / 模板升级不该反过来卡住任务表写入—
响应多给一个派生字段 workflow_step_name步骤名不在 workflow_run_steps 里，要按 run 的模板版本取；服务端查一次比前端硬编码九步名可靠（模板可改）—
GET 过滤时不校验 run 是否存在（不存在的 run 返回空列表）列表接口的常规语义；404 只用在写入上如果想要「查一个不存在的 run 报 404」可以加
没限制 run 的状态已完成 / 已归档的 run 下也能补建任务；任务书没说见第十二节 Q2
404 沿用 RUN_NOT_FOUND / STEP_NOT_FOUND和 /api/workflow/runs* 引擎里已有的错误码保持同一套—
没加每批条数上限与上一轮 /api/tasks/batch 一致；1MB 请求体是天然上限—
