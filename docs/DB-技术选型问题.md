# Soda Office 数据库技术选型问题

> 日期：2026-11-12
> 状态：**待决策**（需要 Leo 拍板）

---

## 一句话

`node-sqlite3-wasm` 不支持多进程共享同一个数据库文件。这是当前架构的地基问题，不是能修好的 bug。

---

## 发现过程

Task 2.1（租约制）完成后，我按 GPT 评审的提醒测跨进程并发 —— GPT 原话：

> 不能把 HTTP 层内的并发测试直接等同于跨进程数据库安全。

第一次测（未设 busy_timeout）：

```
8 进程抢同一任务 → 1 成功，7 个抛 "database is locked" 崩溃
```

加上 `busy_timeout = 5000` 后修好了，以为过关。

但在全量 `npm test` 里连着跑，**10 次里挂 3 次**，报错变成：

```
{"error":"disk I/O error"}
```

---

## 定位过程

逐层排除：

| 测试 | 结果 |
|---|---|
| 8 进程只读同一个 db | ✅ 40/40 成功 |
| 8 进程读写同一个 db | ✅ 40/40 成功 |
| 8 进程并发 `CREATE TABLE IF NOT EXISTS` + 迁移探测 | ✅ 40/40 成功 |
| 8 进程并发 `claimTask`（SELECT + UPDATE） | ❌ 5 轮崩 1 个 |

崩溃现场（worker 分阶段上报）：

```
error="disk I/O error"
steps=["importing","opening","pragma","select"]
                          ↑ 崩在打开后第一次读
```

**结论**：不是并发写的问题，是打开连接后的随机读失败。WASM 没有真正的跨进程共享内存，文件锁状态无法跨进程同步，所以随机崩。

之前「偶尔能过」是假象 —— 进程启动时间错开，没真正同时冲线。

---

## 替代方案实测

| 方案 | 跨进程并发 | 崩溃 | 结论 |
|---|---|---|---|
| `node-sqlite3-wasm` v0.8.61（当前） | 随机 `disk I/O error` | 8 进程约崩 1 个 | ❌ 不可用 |
| `better-sqlite3` v13.1.1 | — | 装不上（无 Visual Studio，node-gyp 失败） | ❌ 不可用 |
| **`node:sqlite`（Node 22 内置）** | **100 轮 × 8 进程，每轮恰好 1 个成功** | **0** | ✅ **可用** |

`node:sqlite` 测试方法：同步栅栏（每个 worker 就绪后写 `ready-<slot>`，父进程集齐 8 个再写 `go`），8 个进程在同一毫秒冲线抢同一个任务。

本机现状：Node **v20.19.2**，没有内置 `node:sqlite`（需要 Node 22+）。

---

## 三个方案

### 方案 A：升级 Node 22（推荐）

- **改什么**：装 Node 22，`src/db.js` 把 `node-sqlite3-wasm` 换成 `node:sqlite`
- **影响面**：API 很像（都是同步的），代码改动小；但要重跑全部 72 个测试
- **风险**：`node:sqlite` 当前标注为实验特性，API 未来可能变；本机其他项目也用 Node 20
- **收益**：真正的 SQLite，跨进程正确，零依赖

### 方案 B：保持 WASM，改单进程架构

- **改什么**：Office 服务成为唯一写库进程，Agent 全走 HTTP API
- **影响面**：符合 GPT 评审的建议（「不应该让多个 Agent 直连 SQLite」），但要多写一层客户端
- **风险**：Office 服务挂掉则全线停摆
- **收益**：不换 Node

### 方案 C：开发用 WASM，生产用 Node 22

- **风险**：两套行为不一致，测出来的东西不算数
- **不推荐**

---

## 建议

**方案 A + B 的骨架**：

1. 升 Node 22，用 `node:sqlite`（解决地基正确性）
2. Agent 仍然不直连数据库，一律走 Office HTTP API（解决架构正确性）

两者不冲突，A 解决「库本身能不能扛住并发」，B 解决「Agent 该不该碰库」。GPT 评审明确建议后者，我实测证明了前者必须做。
